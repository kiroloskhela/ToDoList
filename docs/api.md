# HTTP API contract

The REST API is available at `/tasks` and `/board-config`, with equivalent `/api` aliases for the UI. No authorization header is required in the shared-board scope. Write JSON with `Content-Type: application/json`; compressed request bodies are rejected. Maximum body size is 32 KiB. Query parameters are unsupported and return 422.

Every response includes `X-Request-ID` and `Cache-Control: no-store`. JSON successes use `{ "data": ... }`. Task timestamps are UTC ISO strings; IDs are UUIDs and versions are positive 32-bit integers.

| Method | Path | Request | Success |
| --- | --- | --- | --- |
| GET | `/board-config` | No body | 200 configuration |
| GET | `/tasks` | No body | 200 task array ordered by creation time and ID |
| POST | `/tasks` | Title required; description/statusId/priorityId optional | 201 task, `Location`, strong `ETag` |
| GET | `/tasks/:id` | UUID | 200 task and `ETag` |
| PUT | `/tasks/:id` | All four mutable fields; `If-Match` required | 200 replaced task and new `ETag` |
| DELETE | `/tasks/:id` | `If-Match` required | 204, empty body |
| GET | `/health/live` | No body | 200 process status/uptime |
| GET | `/health/ready` | No body | 200 after database query; 503 if unavailable |

## Configuration and task fields

Configuration contains `brandName`, `boardName`, `description`, `defaultStatusId`, `defaultPriorityId`, `titleMaxLength`, `descriptionMaxLength`, `motion`, `statuses`, and `priorities`. Motion contains `enabled`, `durationMs`, `staggerMs`, and `easing`. Status definitions include `id`, `label`, `description`, `color`, `displayOrder`, and `isComplete`; priority definitions include `id`, `label`, `color`, and `displayOrder`.

Resolve status and priority IDs from configuration. Seeded IDs are generated by PostgreSQL, not API constants. POST defaults are read from the current database configuration. Description defaults to an empty string. Title is trimmed and must remain nonempty; title and description limits count Unicode code points. NUL characters, unknown fields, unknown references, and attempts to set IDs, versions, or timestamps return 422.

A complete PUT body is:

```json
{
  "title": "Review the deployment checklist",
  "description": "Confirm rollback steps with the team.",
  "statusId": "11111111-1111-4111-8111-111111111111",
  "priorityId": "22222222-2222-4222-8222-222222222222"
}
```

The UUIDs above illustrate shape; use IDs actually returned by `/board-config`. A task response adds `id`, `version`, `createdAt`, and `updatedAt`.

## Conditional writes

ETags have the strong form `"<task UUID>:<version>"`. Send the tag returned by GET/POST/PUT in `If-Match` for PUT and DELETE. SQL includes both ID and expected version in the write predicate. A successful PUT increments the version once; a failed conditional write changes nothing. Wildcard, weak, multiple, malformed, or wrong-task tags are rejected.

After 412, refresh tasks before trying again. Do not blindly retry a timed-out write: it may have committed. The UI reconciles by fetching the board and retains the draft after form failures.

## Errors and limits

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please check your input.",
    "fields": { "title": ["Give your task a title."] },
    "requestId": "a diagnostic request identifier"
  }
}
```

`fields` is optional. Error messages never expose SQL, connection strings, or stack traces.

| Status | Meaning |
| --- | --- |
| 400 | Invalid UUID, version/tag syntax, or malformed JSON |
| 404 | Missing task/resource |
| 405 | Unsupported task endpoint method; `Allow` supplied |
| 409 | Version exhausted |
| 412 | Existing task changed since the expected version |
| 413 | Body exceeds 32 KiB |
| 415 | Missing/wrong JSON media type or compressed body |
| 422 | Invalid body, unknown fields/references, configured limits, unsupported query parameters |
| 428 | Missing `If-Match` |
| 429 | Rate limit exceeded |
| 500 | Unexpected internal failure |
| 503 | Database connection, statement, or lock unavailable; `Retry-After: 1` |

Default in-memory limits are 300 total requests and 60 writes per minute per IP, including configuration/health/static requests in the general limit. They apply per process. Reverse-proxy deployment requires explicit trusted-proxy and distributed-limit decisions; neither is enabled by default.
